# 一次完整对话的候选调度过程

以下完全虚构，是设计演练，不是已执行日志，也不是原视频逐字还原。

## 场景：付款约定变化及后续纠正

背景 D1：双方此前约定预付 30%，验收后支付 70%。模式：主动提醒，敏感分析优先私密显示。

| 步骤 | 输入或状态 | 系统职责 | 预期产物 |
|---|---|---|---|
| 1 | U1：这次希望发货前把款付清 | 维护状态 v1，识别新增付款条件 | 候选 C1，尚不能认定对方违约 |
| 2 | 检索 D1 | 对比付款时点和比例 | 原约定与新提议的引用 |
| 3 | Router 选择条件分析 | 检查差异及未明确的交付保障 | 建议确认是否正式修改约定 |
| 4 | Reviewer 检查 | 防止把“希望”写成“已经变更” | 可发送的简短候选 |
| 5A | 无新解释，仍为 v1 | 检查模式、重复、敏感度 | 私密提示付款提议发生变化，附追问 |
| 5B | U2：不是改合同，只是在问能不能提前，仍以验收为准 | 更新 v2，关联 C1 | 未发送则取消；已发送则标记澄清，不继续宣称合同已改 |
| 6 | 用户问：为什么要提醒？ | Dialogue 读取 C1 与来源 | 解释提议和既有约定不同，不指责对方欺诈 |
| 7 | 用户问：接受有什么影响？ | 按需经营分析 | 解释付款暴露的条件性影响，缺少金额和保障时不编造损失 |
| 8 | 用户决定：不改，保留原条款 | 记录有来源的决定 | 候选情节记忆，关联 D1 和发言 |

## 关键设计区别

“出现条件变化”与“必须立即提醒”不同。C1 可以成立，但后续解释可能使提醒失去价值。检测结果、分析结果和发送决策应分别记录，便于解释误报来自哪一步。

## 求职展示可讨论的问题

1. 为什么不让每个 Agent 直接发消息？避免冲突、重复、越权与过时结果。
2. 为什么既有摘要又保留原文？摘要用于缩小上下文，事实依据回查原文。
3. 为什么不能按 Agent 投票？共享同一错误输入可能形成一致错误。
4. 为什么先做回放？分离识别、推理与通知错误，稳定复现时序问题。
5. 多 Agent 是否必要？必须与单模型加检索基线比较，可能实验后简化。

这些是设计问题的回答方向，尚不能作为已经实现的简历成果。
